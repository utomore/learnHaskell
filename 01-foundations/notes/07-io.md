# 第 7 章 — IO:純核心、薄 IO 殼

## IO 是什麼

`IO a` 的意思是「一段執行後會產生 `a` 的**外界互動描述**」。
型別系統把「會碰外界的程式碼」和「純函式」分開 ——
看簽名就知道一個函式會不會有副作用,這是 Haskell 最實用的保證之一。

```haskell
getLine       :: IO Text        -- (用 Data.Text.IO 的版本)
TIO.putStrLn  :: Text -> IO ()
TIO.readFile  :: FilePath -> IO Text
```

`()` 讀作 unit,「沒有有意義的回傳值」。

「描述」這個字要認真看:`TIO.putStrLn "hi"` 這個**值**不會印出任何東西,
它只是「印 hi」這個動作的描述,像一張還沒執行的指令卡。
只有被接到 `main` 上的描述才會在程式跑起來時執行。所以:

```haskell
ghci> action = TIO.putStrLn "hi"    -- 什麼都沒印
ghci> action                         -- ghci 執行它:印出 hi
hi
ghci> action >> action               -- 描述可以組合:印兩次
hi
hi
```

這也是為什麼 `IO a` 的值可以放進 list、當引數傳、存在 record 裡 —— 它就是普通的值。

## do 記法

```haskell
main :: IO ()
main = do
  TIO.putStrLn "你的名字?"
  name <- TIO.getLine            -- <- 執行動作並取出結果
  let greeting = "你好," <> name  -- let = 純計算,不用 <-
  TIO.putStrLn greeting
```

- `x <- action`:執行 `IO a`,把 `a` 綁定給 `x`。
- `let y = expr`:純綁定,沒有執行任何動作。
- 現在把 `do` 當「依序執行」理解就夠了;它背後的一般化(Monad)第 2 級才教,
  **不需要先懂 Monad 才能寫 IO**。

兩個初學者天天犯的錯:

- `name <- "小明"`:`<-` 右邊必須是 `IO 什麼`,字串不是。純值用 `let`。
- `let name = TIO.getLine` 然後把 `name` 當 `Text` 用:`name` 是「讀一行」這個**動作**,
  不是讀到的那一行。要結果就得 `<-`。

`do` 區塊的最後一行必須是一個 `IO` 動作(它是整個區塊的值),不能是 `let` 或 `x <- ...`。

## 鐵則:lazy IO 已淘汰

```haskell
import Data.Text.IO qualified as TIO

content <- TIO.readFile path     -- ✅ 嚴格:一次讀完,檔案立刻關閉
content <- Prelude.readFile path -- ❌ lazy IO:檔案何時讀、何時關不可預測
```

`Prelude.readFile` 回傳惰性的 `String`,實際讀檔發生在「未來某次求值」,
造成 handle 洩漏與不可預測的錯誤時機。**一律用 `Data.Text.IO`**;
超大檔案之後用 streaming(第 3 級)。

### lazy IO 的來龍去脈

Haskell 98 的 `readFile`/`hGetContents` 設計成惰性,是有道理的:
1990 年代的想法是「檔案就是一條 `[Char]`,程式是 `String -> String` 的純函式,
`interact` 把 stdin 接進來、stdout 接出去」。惰性讓這條 list 可以邊讀邊處理,
不用先把整個檔案載進記憶體 —— 在沒有 streaming 函式庫的年代,這是唯一的方法。

代價是**把 IO 藏進純值裡**:`hGetContents` 回傳的 list 每被求值一節,
底層就偷偷做一次讀檔。於是:

- 檔案 handle 要等 list 被完整消費(或被 GC)才會關。你永遠不知道那是什麼時候。
- 讀檔失敗的例外會從「消費 list 的任何地方」冒出來,而不是 `readFile` 那行。
- 最經典的坑:讀了檔案想把處理結果寫回同一個檔案 ——

```haskell
main = do
  s <- readFile "zh.txt"          -- lazy IO:檔案還沒真的讀,handle 還開著
  writeFile "zh.txt" (s ++ "\n")  -- 想寫回同一個檔案
```

```
ch7lazy.exe: Uncaught exception ghc-internal:GHC.Internal.IO.Exception.IOException:

zh.txt: withFile: resource busy (file is locked)
```

`readFile` 的 handle 還抓著檔案,`writeFile` 開不了。這在 Windows 上尤其嚴重
(檔案鎖定連刪都刪不掉)。改成 `TIO.readFile`(嚴格)就沒事,因為它回傳時檔案已讀完並關閉。

社群花了十幾年才放棄 lazy IO,原因是替代品(`conduit` 2011、`pipes` 2012、`streamly` 2017)
要成熟到能取代 `interact` 那種一行搞定的簡潔,需要時間。2026 的結論很清楚:
小檔案用嚴格讀取、大檔案用 streaming,lazy IO 只在舊程式碼裡出現。

## Windows 編碼陷阱(這台機器一定會遇到)

GHC 決定文字 IO 編碼的方式是看**系統 locale**。在 Linux/macOS 上這幾乎永遠是 UTF-8;
在 Windows 上它跟著主控台的 code page 走,繁體中文系統預設是 **CP950(Big5)**。
後果是兩件事同時發生:

```haskell
main = do
  TIO.putStrLn "你的名字?"
  content <- TIO.readFile "zh.txt"     -- 一個用 UTF-8 存的中文檔
  TIO.putStr content
```

在 code page 950 的 PowerShell 裡執行:

```
�A���W�r?
ch7.exe: Uncaught exception ghc-internal:GHC.Internal.IO.Exception.IOException:

zh.txt: hGetContents: invalid argument (cannot decode byte sequence starting from 229)
```

1. **輸出亂碼**:`putStrLn` 把中文編成 CP950 的位元組,而 VS Code 終端、
   測試框架、管線另一端的工具幾乎都預期 UTF-8,收到 Big5 位元組就顯示成 `�A���W�r?`。
2. **讀檔直接炸**:`TIO.readFile` 用 CP950 去解 UTF-8 的位元組,
   `229`(0xE5)是「你」的第一個 byte,在 Big5 裡接不出合法字元 → `IOException`。

解法:程式一開始就把 locale 和標準輸出全部釘死成 UTF-8。

```haskell
import GHC.IO.Encoding (setLocaleEncoding, utf8)
import System.IO (hSetEncoding, stderr, stdout)

main :: IO ()
main = do
  setLocaleEncoding utf8      -- 之後開的所有 handle(含 readFile)都用 UTF-8
  hSetEncoding stdout utf8    -- stdout/stderr 已經開了,要另外設
  hSetEncoding stderr utf8
  ...
```

同一支程式加上這四行之後,在 CP950 主控台裡輸出正常、讀檔成功。
本專案三級的 `test/Main.hs` 開頭就是這段 —— 沒有它,中文測試名稱會變亂碼、
讀 UTF-8 檔案的測試會炸。**你自己寫的每個 `main` 都加上這段**,
它在 Linux/macOS 上是無害的 no-op。

順帶一提 `Data.Text.Encoding` 的 `decodeUtf8`/`encodeUtf8`:如果你走 `ByteString` 讀檔
(第 6 章的表格),編碼是你自己在程式裡明確決定的,完全不受 locale 影響 ——
這是需要精確控制時的做法。

## 架構:純核心、薄 IO 殼

把邏輯寫成純函式,`main` 只做輸入輸出。看本套件的 wordcount:

```haskell
-- src/Examples/WordCount.hs — 全部是純函式,可直接單元測試
stats  :: Text -> Stats
render :: Stats -> Text

-- app/Main.hs — 只有膠水
main = do
  args <- getArgs
  case args of
    [path] -> do
      content <- TIO.readFile path
      TIO.putStr (render (stats content))
    _ -> putStrLn "用法: wordcount <檔案路徑>" >> exitFailure
```

跑跑看:

```powershell
cabal run wordcount -- notes/01-first-steps.md
```

這個「functional core, imperative shell」原則會一路延伸:
遊戲的每幀更新是純函式 `update :: Input -> World -> World`,
IO 殼只負責讀輸入與渲染。ECS(第 5 級)就是這個思想的工業化版本。

為什麼堅持這樣切?因為**純函式可以直接測、直接在 ghci 裡玩、可以放心重構**,
而 IO 程式碼三件事都難。把 IO 壓到最薄,就是把「難測的部分」壓到最小。
一個實用的判斷法:看每個函式的簽名,`IO` 出現的函式應該少到數得出來。

## ghci 實驗

```haskell
ghci> import Data.Text.IO qualified as TIO
ghci> :t TIO.readFile              -- FilePath -> IO Text
ghci> :t TIO.putStrLn              -- Text -> IO ()
ghci> import System.Environment (getArgs)
ghci> :t getArgs                   -- IO [String]         (舊 API,回 String)
ghci> action = TIO.putStrLn "hi"   -- 沒有輸出:只是描述
ghci> action >> action             -- 執行:印兩次
hi
hi
```

## 常見誤區

1. `<-` 右邊放純值、`let` 左邊放 IO 動作。
2. 把 `TIO.getLine` 這個動作當成讀到的字串。
3. 在 Windows 忘了 `setLocaleEncoding utf8`,中文一出現就亂碼或炸。
4. 用 `Prelude.readFile` 讀完再寫同一個檔 → `resource busy (file is locked)`。
5. 想「在純函式裡順便印個 log」→ 做不到,這是刻意的;要 debug 用 ghci 直接呼叫純函式看結果。

## 2026 實務準則

1. 文字 IO 一律 `Data.Text.IO`,不用 `Prelude` 的 `readFile`/`putStrLn`。
2. `main` 開頭固定 `setLocaleEncoding utf8` + `hSetEncoding stdout/stderr utf8`。
3. 純核心、薄 IO 殼;`IO` 出現在簽名裡的函式越少越好。
4. 大檔案不要一次 `readFile`,第 3 級的串流章處理。
